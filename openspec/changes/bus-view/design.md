# Design

## Context

See proposal.md for why, and for every measured number this design leans on. The code it joins, as
#40 left it:

- `src/live/feed.ts` is pure (decode, validate, merge, age) and scanned by `src/sim/purity.test.ts`.
  `src/live/poll.ts` fetches on a 2 s tick, gated by `due()`, each feed once a minute and 30 s apart.
- `useLive` holds per mode the held fixes (newest per vehicle), a version and a status. Nothing
  subscribes to the fixes; the frame loop reads them with `getState()`.
- `src/map/live.ts` draws each mode as one `IconLayer` (flat arrow for buses, disc for KTM), coloured
  per map style from `LIVE_STYLE`, rebuilt only when the version, the stale set, the zoom band or the
  style changed. Live layers go first in `setProps`, so rail draws over them.
- `MapView` keeps the map style as React state plus `modeRef`; the frame loop reads the stores with
  `getState()` every frame. Counts, status lines and the open card are painted through refs on a
  quarter-second gate (`readout.ts`). Hover text is written by `showTip` from deck.gl's `onHover` only.
- Trains are `ScenegraphLayer`s of glTF models generated by `scripts/build_train_models.mjs`: +X
  forward, +Y left, +Z up, metres, shading baked into an 8x1 palette texture because `getColor`
  replaces `baseColorFactor` and multiplies a texture. Scaled by `W / MODEL_W` for a constant screen
  size. `pointAt(line, at, reversed)` in `src/sim` turns metres along a path into lon, lat, bearing.
- The daily workflow downloads the rail feed, rebuilds `data/network.json`, runs
  `check_feed.py --self-test`, and commits only when the data changed.

## Goals / Non-Goals

**Goals**

- Every rule that decides where an estimated bus is drawn is pure, takes time as an argument, and is
  tested with fixed inputs, like `src/sim`.
- First paint is unchanged in both views: the main bundle grows by a small route-name table only, and
  everything else loads after the map has drawn.
- No new per-frame React work; no new dependency.
- Built in four stages, each looked at by the owner and merged before the next starts.

**Non-Goals**

- Arrival predictions, trip updates, bus timetables in cards, or a stop's departures. A stop says its
  name, nothing more.
- Drawing every bus route. Only the selected bus's shape is drawn, because it shows what the estimate
  assumes.
- Estimating KTM ETS. Its bearings and speeds are placeholders, KTMB publishes no shapes, and a fix
  moves every 120 s over intercity distances: there is nothing honest to move it along.
- MRT feeder buses (`rapid-bus-mrtfeeder`), a separate feed.
- Following a bus with the camera. Possible once buses move smoothly; a follow-up if wanted.

## Decisions

### One change, four stages

Confirmed by the owner: each stage is built, looked at by the owner, and merged before the next
starts. Each task group ends with that look and its pull request (`Refs #43`; the last says
`Closes #43`).

1. **Archive, static bus data and route numbers.** First archive the three merged changes still in
   `openspec/changes/` — `live-buses-ktm` (#44), `interchange-places` (#42) and `station-labels` (#45)
   — so `live-vehicles`, `places` and `station-labels` reach `openspec/specs/` and this change's deltas
   have something to modify. All three validate with `--strict` today. Care points: archive in merge
   order (#42, #44, #45); `live-buses-ktm` MODIFIES `inspection`'s "Pointing at something says what it
   is" and `station-labels` ADDS "A station can be found by name" to the same spec, and both must
   survive. `live-buses-ktm` has two open tasks, moved here as 9.1 and 9.3 with a note in its tasks.md.
   The owner's main checkout shows `station-labels`' two spec files deleted but uncommitted, so the
   archive is done on this stage's branch from the committed files, and that working tree is left for
   the owner to explain. `station-models` is NOT archived: it is unbuilt and its approach was rejected
   (CLAUDE.md, "WE DRAW NO STATION GEOMETRY"). Then the script, generated files, checks, refresh, and
   route numbers in #40's hover and card: "300" instead of `U3000`.
2. **The view switch and bus stops.** Rail/Bus switch, rail dimming, stops loaded on first entry to
   the bus view. Buses are still #40's markers at their fixes.
3. **Models.** Bus and ETS models, drawn where the views say.
4. **Motion.** Background loading of shapes, `estimate.ts`, the estimate wording and countdown, the
   selected route shape, polling at 30 s, the honesty text, CLAUDE.md.

Stage 4 is the only one that changes what a position means, so it is last and reviewed on its own.

### Motion in both views, once the shapes have arrived

The owner's call: buses move in both views. In the rail view they stay small flat arrows beneath the
network, now placed and turned by the estimate; in the bus view they are models. The estimate is the
same code and the same state in both, so switching view never moves a bus.

Until the shapes arrive, and for any bus that cannot be estimated, a bus is exactly what #40 draws: at
its last report, never called estimated. The card, hover and caption decide their wording from
whether THAT bus is drawn at an estimate, not from the view.

### Where the switch sits, and where the view lives

Next to the City/Wireframe switch, as a two-option radio group (`<fieldset>` with two native radios,
so arrow keys, focus and announcement come free). Both choices answer "what is this map of", both apply
to the whole map, and both must be reachable on a phone, where the lines panel starts closed. The
lines panel is for per-line and per-mode detail; putting a whole-map choice inside it would hide it.

The view (`'rail' | 'bus'`) lives in `useView`, beside `hidden` and `liveOff`, remembered in
`localStorage` like the map style. It is React state because a person changes it; the caption in
`App`, the lines panel and the switch subscribe to it. The frame loop reads it with
`useView.getState()`, as it already does for `hidden` every frame — a ref would do the same job, but a
store field is the pattern the loop already follows and needs no prop threading. It is also written to
`document.documentElement.dataset.transitView`, as the map style is, so CSS can follow it.

### Dimming rail in the bus view

deck.gl's layer `opacity` prop on the rail layers (lines, shared corridor, stations, trains, station
names), one constant `BUS_VIEW_RAIL_OPACITY` beside `LIVE_STYLE`, tuned by eye in both map styles. The
static layers are rebuilt when the view changes, exactly as they are when `hidden` changes — not per
frame. Trains are rebuilt every frame already and take the opacity as an argument. Dimmed layers stay
pickable: an interchange is exactly where a viewer wants to click from a bus to a train.

Draw order in the bus view: rail (dimmed), stops, buses, KTM, names. In the rail view it stays as
today: live markers first, then rail. Alternative considered: hiding rail entirely — rejected by the
issue, because interchanges are the point.

### Static bus data: three generated files, split by when they are needed

`scripts/build_bus_json.py FEED_DIR OUT_DIR`, pandas like the rail script (quoted CSV fields with commas
are real in this feed), writes:

| File | Holds | Size (raw / gzipped) | Loaded |
|---|---|---|---|
| `data/bus-routes.json` | route id to `[short name, long name]` | about 10 KB | in the main bundle: route names show on every bus hover, in both views, from the first fix |
| `data/bus-shapes.json` | `origin` (the same projection as `network.json`), shapes simplified with the rail script's Douglas-Peucker at 5 m and rounded to 5 decimal places, trip id to shape id | about 515 KB / 126 KB | in the background after the map first goes idle, in both views, while buses are on |
| `data/bus-stops.json` | stops as `[id, name, lon, lat]` | about 232 KB / 73 KB | on first entry to the bus view |

Why split shapes from stops rather than one file: they are needed at different times. Motion runs in
both views and stops only in the bus view, so one file would make every rail-view visit download 73 KB
of stops it never draws. Two files also fail separately: no stops does not stop buses moving, and no
shapes does not hide the stops. The route table stays in the bundle because it is small and needed
before either. The trip-to-shape table rides with the shapes because it is useless without them, and
7 KB gzipped.

Why every shape and not only routes seen live: any route can appear at any time, and all 171 shapes at
5 m are 119 KB gzipped against 53 KB for the 70 seen in one afternoon. Integer delta coding could
roughly halve the file later if it matters on phones; not now.

Stop names are kept as published (ALL CAPS). The rail script's prettifier exists, but its keep-list is
tuned to station names; applying it to 4,000 street names would get some wrong silently.

The trip-to-shape table is shipped rather than parsed out of the trip id. Every current trip id does
spell its route and shape (`weekday_U6000_U600001_9`), but that is a convention nobody promised, and
parsing it would be guessing.

### Loading: `?url` and `fetch`, after first paint and on first bus view

`import shapesUrl from '../../data/bus-shapes.json?url'` (and the same for stops) makes Vite emit each
as a content-hashed asset, and `fetch` loads it. Shapes: once, on MapLibre's first `idle` event after
the overlay is added (style, first tiles and first deck.gl frame drawn), provided buses are switched
on; otherwise when they are first switched on. Stops: once, the first time the view is `bus`.
Alternatives considered:

- **Bundling**: delays first paint on every visit. Ruled out by the owner.
- **Dynamic `import()` of the JSON**: turns 500 KB of data into a JavaScript module to parse, kept in
  the module graph for good. `JSON.parse` of a fetched body is faster and fails as an ordinary rejected
  promise we report.
- **Loading shapes on the first bus fix**: the first fix usually arrives before the map has drawn, so
  it would compete with the tiles. `idle` is later and certain.
- **A copy in `public/`**: the stale-copy problem Milestone 1 removed for `network.json`.

Each file's state (`idle | loading | ready | failed`) sits in `useLive` and the lines panel paints it.
A shapes failure says estimated movement is unavailable; a stops failure says stops are unavailable
(spec: bus-view).

### Stops

One `ScatterplotLayer`: small filled circles with a contrasting outline, pixel-sized, colours per map
style in `LIVE_STYLE`. Built once when the data arrives; `visible` is false below zoom 14 and in the
rail view, so zoom changes cost nothing. Pickable, for the hover name only; a click on a stop selects
nothing (no card, because there is nothing honest to put in one yet). At 4,053 stops, at most a few
hundred are in view from zoom 14.

The base map's `poi_transit` layer, which in KL is bus stops, gets `visibility: none` in the bus view
through the same `layerOps` path the map style uses — visibility only, never a filter, which the
existing test already holds.

### Motion: predict, then correct (`src/live/estimate.ts`)

Pure, scanned by `purity.test.ts` (its glob widened to this file). One instance serves both views.
Positions are metres along a prepared shape; `pointAt` turns them into lon, lat and bearing. `pointAt`'s parameter is narrowed from
`PreparedLine` to the fields it reads (`origin`, `xs`, `zs`, `cum`, `total`), so a bus shape prepared
the same way can use it; that is a type change in `src/sim`, covered by the golden tests.

In five lines:

1. A fix is placed on its trip's shape: every place within 50 m, clustered, and kept only if the
   shape's direction there is within 60 degrees of the bus's bearing (this resolves the round-trip
   shapes in 83 of 89 and 124 of 132 cases); after the first fix, the candidate just ahead of the last
   place (allowing 60 m back for GPS noise) wins.
2. Speed is the along-shape distance between the last two fixes on the trip over their time gap,
   times `SPEED_FACTOR` (0.5); the estimate is `place + speed × min(now − fixSec, 150 s)`, clamped to the shape's end.
3. On a new fix, what is drawn catches up forward over 4 s, stands still if the new estimate is up
   to 250 m behind until it passes, and jumps if more than 250 m behind, on a new trip, or when a held
   bus's new estimate stops short of it.
4. It stops: 150 s after the fix it starts from, at the end of the shape, and not at all without a
   usable shape (unknown trip, over 50 m off, one fix only, ambiguous place, or over 90 km/h).
5. It is described everywhere as estimated, with the real fix's age and a countdown to the next check.

The data it works on:

- **Track** (per bus, replaced when a fix arrives): trip and shape id, the last fix's place along the
  shape (or none), its time, the previous place and time on the same trip, and the measured speed (or
  none). `onFix(track, fix, shape) → track` is the only way it changes.
- **Drawn** (per bus, advanced each frame): the place drawn, and whether it is following, catching up
  (from where, since when) or holding. `drawnAt(drawn, track, nowMs) → drawn`.

The frame loop keeps both maps inside `liveLayers`'s closure, as it keeps built layers now, and calls
`onFix` only for buses whose `fixSec` changed since the last version. It forgets both when buses are
switched off or the clock leaves live, like the layer instances.

**The constants**, each a named export with its measurement beside it, all calibration rather than
contract:

| Constant | Value | From |
|---|---|---|
| `SPEED_FACTOR` | 0.5 | the owner prefers fewer pauses to less lag; see "How fast an estimate moves" below. Tunable by eye |
| `PREDICT_S` | 150 | fix-to-fix gap median 60 s, p90 90 s, plus header lag median 27 s and up to 30 s of polling: a normally reporting bus's next fix lands within about 150 s |
| `OFF_ROUTE_M` | 50 | fix-to-shape distance p95 25 to 38 m |
| `BEARING_TOL_DEG` | 60 | bearing against shape direction: median 3.3 degrees, p90 19 degrees |
| `HOLD_MAX_M` | 250 | at 0.5, 2 to 3% of fixes land more than 250 m behind. Standing 250 m at 17 km/h is about 50 s, a long red light |
| `CATCH_UP_S` | 4 | taste |
| `MAX_KMH` | 90 | tracked speeds p99 60 to 66 km/h; the feed's own maximum 81.7 km/h; anything above is a mismatched place |

Expected behaviour at 0.5: about 80% of new fixes land ahead and the bus catches up forward, 16 to
21% land behind and it pauses, 2 to 3% jump back.

### How fast an estimate moves

Measured on the owner's review of this plan. A backtest replays real fixes: for each bus with three
distinct consecutive fixes on one trip, it takes the along-shape speed between the first two, applies
the factor, predicts where the third fix should be (capped at 150 s, speeds over 90 km/h skipped, as
the estimate does), and compares that with where the third fix actually was.

- **Error**: the distance along the route between prediction and fix (median).
- **Lands behind**: the fix is more than 5 m behind the prediction, so the drawn bus pauses (or, beyond
  250 m, jumps back).
- **Lag**: fix minus prediction, signed, median; positive means the drawn bus trails the real one when
  the fix arrives.

Two fresh samples, polled every 30 s: A, 14:42 to 14:46 KL (4 distinct responses, 200 triples) and B,
15:00 to 15:05 KL (5 distinct responses, 285 triples), all in `samples/`. **The two #40 fixtures give
no triples**: they are two responses two minutes apart, so no bus has three fixes in them. They were
used for the shape-fit and bearing figures only. A and B are not pooled, because the 15-minute gap
between them would make false triples.

| Factor | A: error | A: lands behind | A: >250 m behind | A: lag | B: error | B: lands behind | B: >250 m behind | B: lag |
|---|---|---|---|---|---|---|---|---|
| 1.0 | 131 m | 46% | 15% | 1 m | 113 m | 45% | 14% | 1 m |
| 0.8 | 149 m | 33% | 7% | 69 m | 124 m | 34% | 9% | 46 m |
| 0.7 | 139 m | 28% | 5% | 102 m | 128 m | 28% | 6% | 69 m |
| 0.6 | 161 m | 23% | 4% | 133 m | 151 m | 26% | 4% | 96 m |
| **0.5** | **178 m** | **16%** | **3%** | **168 m** | **154 m** | **21%** | **3%** | **126 m** |
| 0.4 | 208 m | 13% | 1% | 206 m | 176 m | 14% | 1% | 158 m |
| hold still (#40) | 343 m | 1% | 0% | 343 m | 275 m | 1% | 0% | 275 m |

**The pick is 0.5.** Across both samples it cuts "lands behind" from about 34% at 0.8 to about 19%,
which is roughly half, and its median error (178 m and 154 m) is about half of holding still (343 m and
275 m). The price is lag: when a fix arrives the drawn bus is typically 130 to 170 m behind it, and
catches up forward over `CATCH_UP_S`. 0.4 halves the pauses more surely (13 to 14%) for another 30 to
40 m of lag; it is the next step if the owner still sees too many pauses. `SPEED_FACTOR` is taste
within this table, tuned by eye in task 12.2 and re-measured in 12.1. The "never glide backwards" rule
does not depend on it.

Why not snap forward only, or ease backwards: easing back is a bus driving backwards, which the owner
ruled out; never correcting back would leave buses up to 500 m ahead of the truth. Holding is what a
real bus at a light looks like, which is why it is the common case.

Why a place on the shape and not the raw fix: the estimate has to move along something, and a bus
drawn a few metres beside the road it is moving along would look wrong. Fixes are within 5 m of their
shape at the median; beyond 50 m nothing is moved onto the shape.

### Polling: 30 s and 120 s, at least 10 s apart

`POLL_MS` becomes per mode, `{ bus: 30_000, ktm: 120_000 }`, and `STAGGER_MS` becomes a minimum gap
of 10 s between any two requests. With the 2 s tick that gives buses at 0, 30, 60 s and KTM squeezed
between them: 2.5 requests a minute, and never more than 3 in any 60 s window. That invariant is a
test that simulates ten minutes of ticks through `due()`.

The countdown needs the next request's time. `poll.ts` exports `untilNextMs(mode)` from its
module-level `last` times; the card paints it through a ref on the existing quarter-second gate. The
countdown is to the next CHECK, not to the next fix: the bus feed changes only every 60 to 80 s, so
half the checks bring nothing new. To say so, each held vehicle records when its current fix was
received (`mergeFixes` gains a `receivedMs` argument), and the card says "no newer report at the last
check" when the feed's last good answer is later than that.

### Models: a rigid bus, and a directionless ETS marker

Both generated by `scripts/build_train_models.mjs`, same palette texture, same axes, same scale
convention (`W / MODEL_W`), and both added to `models.test.ts`:

- **Bus**: one rigid body (Rapid KL's fleet is mostly 12 m single-deck), about 9 m long, 3.4 m wide,
  3.4 m tall — shorter and wider than real, for the reason the trains are. The front is tapered and
  carries the `CAB` shade, the back does not, so the direction is readable. Drawn at ground level
  (z = 0), tinted `LIVE_STYLE.color[style].bus`, one neutral for every route, so it cannot be taken
  for the line-coloured, articulated, elevated BRT Sunway model. Oriented by `yawFor(bearing)` along
  the shape's direction while estimated, and by the reported bearing when drawn at a fix.
- **ETS**: an octagonal puck about 7 m across and 3 m tall, banded (dark skirt, pale roof), ETS
  magenta, yaw fixed at 0. Every elongated model has an axis, and an axis on a map is a claim about
  which way the track runs; the feed's bearing is a placeholder and KTMB publishes no shapes, so there
  is nothing true to align it to. A near-round shape with eight-fold symmetry makes no such claim, and
  is still a 3D object in the scene rather than a flat disc. `models.test.ts` checks the bus lies
  along +X like the trains, and that the ETS model's X and Y extents are equal.

Considered for ETS: a train model aligned to the direction between its last two fixes. Those are
120 s and up to 4 km apart, on curving intercity track, so the heading would be an average that is
wrong on every curve; and a train that has only reported once would need a second form anyway.
Rejected as more machinery for a claim we cannot back.

Stale models cannot be "hollow" as #40's markers are, so stale is lower alpha and a grey-shifted
colour, both in `LIVE_STYLE`, checked by eye in both styles. The rail view keeps #40's hollow arrow
for stale buses.

ETS uses its model in both views (dimmed with rail in the bus view, since it is a train). Buses use
models in the bus view and #40's arrows in the rail view; both move on the same estimate.

### The hover tooltip that froze

`showTip` runs only in `onHover`, which deck.gl fires only when the pointer moves, so a still pointer
kept "45 s ago" for ever. The fix: `onHover` also records what is hovered (layer id, vehicle mode and
id, pointer position) in a ref, and the quarter-second gate repaints the tip from it while it names a
live vehicle. A moving bus can leave a still pointer behind; the tip keeps naming it until the pointer
moves, which is accepted — it is still that bus's true age.

### Checks for the bus data

`scripts/check_feed.py` gains `check_bus(bus, routes, old)` and a second list of break-it cases, run by
`--self-test` like the rail cases, and invoked with `--bus DIR [--against-bus DIR]`. The rules are the
ones the spec lists. "Far fewer" is under half of the stored count, a truncation guard that a real
network change will not trip (a bus network does lose and gain stops; rail's "any fewer" rule would
reject that). The box and null-island test reuse the live feed's box and its 0.1 degree radius,
duplicated in Python with a comment pointing at `feed.ts`. `npm run check:feed` gains the bus
arguments; the workflow downloads the bus feed, builds into temporary files, checks, and commits all
four data files in one commit when any changed.

Pinned values measured from this snapshot (4,053 stops, 137 routes, `U3000` is `300`) go in `npm
test`, never in the checks.

## Risks / Trade-offs

- [Estimates trail the real bus by a median of 130 to 170 m at 0.5, and 2 to 3% of corrections jump
  back more than 250 m]
  → Said on every card and hover, the constants are named and tunable, the owner looks during service,
  and the selected bus's route is drawn so the assumption is visible.
- [The samples are one weekday afternoon, 485 triples in two sets] → The 08:00 and 23:30 re-sample
  task also re-runs the backtest, and the constants move with it in the same commit.
- [Buses at street level are hidden by 3D buildings close in] → The same trade the trains make; bus
  view dimming does not change it. Looked at in the owner's check.
- [A bus off its route (detour, depot run) sits still while others move] → That is the honest answer;
  its card says why.
- [Loop shapes whose bearing does not settle the place] → 6 to 8 of every 100 ambiguous fixes; those
  buses wait one fix before moving.
- [Shapes are 126 KB gzipped on every visit with buses on, in both views] → After first paint, so
  the map never waits for them; buses sit at their fixes until they arrive, which is #40's behaviour.
  Integer delta coordinates could halve the file later if phones need it.
- [Shapes load after `idle`, which a slow tile server can delay] → Buses stay at their fixes, honestly
  labelled, until then. Nothing waits on it.
- [A trip missing from static GTFS, like `weekday_T7890_T789002_2` today] → No motion for that bus,
  and a count of such buses in the bus status line, so the gap is visible rather than silent.
- [30 s polling spends more of a shared rate limit (office or carrier NAT)] → 2.5 a minute leaves 1.5;
  a 429 is stated and held buses keep ageing, as today.
- [Archiving `live-buses-ktm` with two open tasks] → They are carried here explicitly; the archive
  notes where they went.
- [Three archives in one pull request, two touching `inspection`] → In merge order, each validated
  first, and the resulting `inspection` spec read for both requirements before stage 1 is merged.

## Migration Plan

None. Additive. The view defaults to rail, which is today's map with moving buses from stage 4. Rollback is reverting the pull
request(s); the generated bus files can stay in `data/` harmlessly, and the workflow step that builds
them is reverted with the rest.
